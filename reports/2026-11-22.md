## 1. Yoroll

▲ 365 票 · 💬 34 条评论 · [Product Hunt](https://www.producthunt.com/products/yoroll) · [官网](https://app.yoroll.ai/)

> **⚠️ 本条未通过质检（得分 74），以下问题请自行核实：**

### ① 一句话说清楚
把一段故事或视频变成能点选分支、有不同结局的互动小游戏。

### ② 它解决了什么痛点

- 谁在用：写短剧的编剧、做 AI 视频的创作者，以及脑子里有故事但不会写代码的人。资料里提到团队在 GDC 和 NVIDIA GTC 上反复听到“我一直想做游戏，但不知道从哪开始” [已知]。这两类人具体是谁，资料只给了“写短剧或做 AI 视频的人”这个范围 [已知]。
- 在什么场景下遇到了什么麻烦：假设你拍了一段短剧，主角在剧里签了一份合同。你想让观众能选择“让她转身离开”，于是需要补拍一个离开的镜头，还要让这条新分支能接回原来的剧情。以前要在游戏引擎里把这一条选择做出来，是最麻烦的环节，资料原话是“getting that one choice to work on screen is where things get fiddly” [已知]。
- 以前大家怎么凑合解决：资料没有描述用户过去的具体替代方案，只提到传统做法需要游戏引擎 [已知]。可以合理推断，不会写代码的人要么放弃互动设计，要么找人代做 [推测]。这样不好的地方在于费时、需要额外技能，而且改一次分支就要动一次工程 [推测]。
- 痛点有多“痛”：资料没有给出使用频率或付费数据。产品设有 Black Friday 会员折扣，说明存在付费会员制 [推测]。用户是否愿意为此付钱、付多少，资料未提及 [推测]。从团队在游戏开发者大会和英伟达技术大会上反复听到同一句话来看，这个需求在创作者中不算罕见 [推测]。

### ③ 它是怎么做到的

- 产品形态：网页应用，入口是 app.yoroll.ai [已知]。站内分成几块：Yoroll Agent（能自己拆步骤、调用工具办事的 AI 助手） 负责从故事到分镜再到视频的流程；Yoroll Code 用来做独立小游戏或故事里的可玩片段；还有一个互动短剧工具，用来在已拍好的素材上增加分支 [已知]。使用流程大致三步：第一步，把故事前提、剧本或几张参考图交给 Yoroll Agent；第二步，梳理每个选择通向哪里，检查分镜，挑出要转成视频的镜头；第三步，自己玩一遍看效果，然后发布分享 [已知]。在 Yoroll Code 里，流程是描述一个玩法（比如“在守卫回来前撬开锁”）、在浏览器里试玩、调整计时器再试 [已知]。
- 技术原理：输入是文字剧本、图片或视频片段 [已知]。处理环节由 AI 把素材组织成带分支的互动体验，资料的说法是“AI helps bring everything together” [已知]。输出是一个可以分享、可以玩的互动作品 [已知]。资料提到的具体能力包括：生成视频（Seedance video）、生成 3D 内容（Tripo 3D）、生成音效，以及把游戏引擎放进同一个工作区 [已知]。这些能力各自怎么实现、是不是自研，资料未提及。
- 推测的技术栈：
  - 前端：网页应用，浏览器内可试玩，具体框架资料未提及 [推测]
  - 后端：资料未提及，仅知有账号与会员体系 [推测]
  - AI 模型或 API：接入 Tripo 3D 与 Seedance video 等第三方生成能力 [推测]
  - 数据来源：用户上传的剧本、图片、视频，以及平台自带的示例作品 [已知]
- 真正的壁垒是什么：单看“AI 生成视频”这一层，市面上有多个供应商，不难替换 [推测]。资料里最能构成差异的是把分镜、分支逻辑、试玩、发布串成一条流程，并且让已有实拍素材也能接进分支 [已知]。这属于工作流和产品整合层面的壁垒，不是单点技术壁垒 [推测]。分发渠道和数据积累方面，资料未提及。

### ④ 对我的启发

- 可迁移的思路一：不要跟最强的模型比生成质量，而是把几个现成能力拼成一条“外行也能走完”的流程。Yoroll 把 3D、视频、音效、引擎放在同一个工作区 [已知]，卖的是省掉来回切换工具的麻烦。
- 可迁移的思路二：从用户手上已有的东西出发。资料强调“start with whatever you've got”，已有短剧素材也能加分支 [已知]。这比要求用户从零开始更容易让人迈出第一步。
- 行业趋势：AI 视频正从“生成一段给人看”走向“生成一段让人玩” （来自团队自述的定位）[推测]。同时，“无代码”工具在把原本属于专业软件的能力下放给内容创作者 [推测]。
- 对想做 DA / DS 的学生：这个产品本质上是把创作过程变成可记录的行为数据——用户在哪个分支停下、选了哪条路、哪个结局被走到最多 [推测]。这类数据适合做漏斗分析和路径分析。可以练的思维是：先定义“一次有效互动”怎么衡量，再谈优化。

### ⑤ 可复现性评估

- 复现难度：★★★★☆ (4/5)。理由：做一个“文字分支 + 选项跳转”的网页 demo 不难；难的是视频生成、3D 生成、音效、引擎同处一个工作区，还要保证分支能接回原剧情 [推测]。
- 学生做出 MVP 需要：前端基础（能搭页面和选项跳转）、一点后端或直接用现成的表格存剧情结构、调用一个视频或图像生成 API 的基础能力 [推测]。大约 40–80 小时 [推测]。必须花的钱主要是生成 API 的调用费，具体价格资料未提及 [推测]。
- 最难的一步：让“新生成的分支镜头”和“原有素材”在视觉与叙事上接得上 [推测]。可降低难度的现成资源：分支叙事可以先用纯文字和图片实现，视频生成部分再单独接入；资料提到的 Tripo 3D 与 Seedance video 是否对个人开放、如何计费，资料未提及，需自行确认。

### ⑥ 基于这个灵感的个人项目（STAR 法则）

**项目名 + 一句话描述**：互动故事的分支结构分析——用公开的问答数据集模拟“分支剧情”，统计不同分支设计下的路径深度与选项文本多样性，做成可交互的看板。

**S (Situation)**：互动叙事产品越来越多，但创作者在动手前往往不知道“分支该做多深、每个节点该给几个选项”才合理 [推测]。这类设计经验目前多靠感觉，缺少可对照的公开数据。

**T (Task)**：在一个公开的问答数据集上，把每道题的多个候选答案当作“同一节点的多个选项”，回答三个可检验的问题：①不同题目的候选答案数量分布如何（选项数直方图与分位数）；②候选答案之间的文本相似度是否与答案数量相关（用 Embedding（把文字变成一串数字，好比较意思是否相近） 算两两余弦相似度，再做相关分析）；③给出“选项数最多且选项间差异最大”的前 10 道题清单。目标是把“选项数”这一结构指标的统计口径固定下来，并产出至少 3 张可解释的图表；不涉及任何用户行为或流失预测。

**A (Action)**：数据来源选用 SQuAD 数据集 https://huggingface.co/datasets/rajpurkar/squad ，该数据集每题自带多个参考答案（answers 字段）和上下文段落，字段明确、可免费下载、无需审批。清洗步骤：去掉 answers 为空的记录、统一小写与标点、按题目 ID 分组、每题只保留去重后的答案文本。方法：先做探索分析（每题答案数的直方图、答案长度的分布），再用 Embedding 计算同一题内答案两两的余弦相似度，取平均值作为“选项差异度”；用皮尔逊相关系数检验“答案数”与“选项差异度”是否相关，并给出置信区间；最后按“答案数”和“选项差异度”排序输出前 10 题。展示用一个 Streamlit（用 Python 快速搭数据网页的工具） 页面：左侧是答案数分布图，右侧点选某题可看到该题各答案的相似度热力图。

**R (Result)**：预期目标：完成至少 3 张图表（答案数直方图、相似度热力图、答案数与差异度的散点图），并给出相关系数的点估计与 95% 置信区间；若相关系数绝对值大于 0.2 且置信区间不含 0，则报告为“存在弱到中等相关”。测量方式：固定随机种子，相似度计算重复 3 次取平均，报告均值与标准差。

**可行性打分**：数据可得性 5/5，SQuAD 字段明确、可直接下载；技术难度 3/5，Embedding 相似度加相关分析属于入门方法；时间成本 4/5，两周 35 小时够用；简历加分程度 3/5，题目清晰但业务解释偏弱。总分如下。
项目可行性：4/5

**两周执行计划**：
- 第 1–2 天：下载 SQuAD，核实 answers 字段，写数据字典。
- 第 3–4 天：清洗，构造题目级特征（答案数、平均答案长度）。
- 第 5–6 天：探索分析，画答案数直方图，人工抽查不超过 60 条记录确认清洗无误。
- 第 7–9 天：用 Embedding 算题内答案两两相似度，得到每题“选项差异度”。
- 第 10–11 天：做相关分析与置信区间，输出前 10 题清单。
- 第 12–13 天：搭 Streamlit 页面。
- 第 14 天：写结论与局限，整理成可讲述的三分钟版本。

**面试可能被追问的 2 个问题**：
1. “把问答数据集的多个参考答案当成剧情分支选项，这个类比合理吗？”回答方向：承认这是结构类比而非真实剧情数据，说明它检验的是“同一节点多选项”的统计规律，并指出若要验证剧情场景需要另找互动叙事数据。
2. “相关系数只有 0.2 左右，这个结论有意义吗？”回答方向：说明弱相关也可能有设计参考价值，重点在于给出置信区间和效应量，而不是只报 p 值；同时承认样本来自问答领域，外推到剧情设计需谨慎。

## 2. Rankhog

▲ 354 票 · 💬 41 条评论 · [Product Hunt](https://www.producthunt.com/products/rankhog) · [官网](https://www.producthunt.com/r/HVFQNHONLRBAJZ)

### ① 一句话说清楚
帮小商家在 Reddit 上找到想买东西的人并自动回复。

### ② 它解决了什么痛点
- 谁在用：独立开发者、小团队创始人，以及自己负责推广、没有专职营销人员的小商家。资料里作者说自己一个人做产品，也把“你的产品”作为服务对象 [已知]。更具体的用户画像资料未提及，以下场景属于合理推断 [推测]。
- 在什么场景下遇到了什么麻烦：设想一个卖笔记软件的人，半夜刷到 Reddit 某个版块有人发帖问“有没有便宜的笔记工具推荐”，等他第二天看到，帖子已经沉了，潜在客户早买了别家。Reddit 上“大家用什么来做 X”这类帖子每天都在出现，相当于客户在公开场合举手 [已知]。难点在于每个版块（subreddit，Reddit 里按主题划分的讨论区）都有自己的规则，新账号发的内容会被删，一条偷懒的推销评论就可能被封号 [已知]。
- 以前大家怎么凑合解决，为什么那样不好：自己手动盯版块、手动写回复，作者原话说“把 Reddit 做好是一份全职工作” [已知]。人工盯梢费时间、容易错过帖子刚发出来的黄金时段，而且不熟悉各版块规则容易踩雷 [推测]。市面上常见的替代是群发广告的机器人，但作者明确说自己的产品不是 spam bot（垃圾信息机器人），不群发、不买账号、不在规则禁止的地方发帖 [已知]，说明这类粗暴做法存在且效果差、风险高 [推测]。
- 痛点有多“痛”：对靠 Reddit 获客的小商家来说，这是高频且直接关系到收入的事 [推测]。作者定价 99 美元每月每个产品，还提供 7 天免费试用 [已知]，说明他认为用户愿意为此付钱 [推测]。但实际付费意愿资料未提及。

### ③ 它是怎么做到的
- 产品形态：主要通过网页应用使用，也能在 Claude、ChatGPT、Cursor 等支持 MCP 的客户端里操作 [推测]。MCP（让 AI 连接外部工具的统一插口，像 USB）意味着用户可以在自己常用的 AI 对话里直接指挥这个工具 [推测]。典型使用流程推测为三步：第一步，接入自己的 Reddit 账号，没有账号的话由产品新建一个并“养号”；第二步，产品自动监控相关版块，找出正在询问你所卖产品的人；第三步，逐条审核它写好的回复并点“同意”，或者打开 autopilot（自动驾驶，即全自动模式）让它自己发 [已知]。
- 技术原理：输入是 Reddit 上各版块的帖子和规则文本 [已知]。处理分几层：先用监控模块（作者叫它 Radar）在目标版块里筛选出“有人在求购”的帖子 [已知]；再让语言模型读懂该版块的规则和讨论风格，写出一条“先帮忙”的回复，并且像严格的版主一样自查一遍，只有合适时才提产品名 [已知]；最后按接近真人的节奏从用户自己的账号发出 [已知]。输出就是一条条待审核或已发布的评论 [已知]。这里用到的 LLM（大语言模型，读过海量文字、会接话和写作的 AI）负责写回复和自查 [推测]，规则理解可能也靠它 [推测]。
- 推测的技术栈：
  - 前端：网页应用，具体框架资料未提及 [推测]
  - 后端：账号养护、定时发布、审核队列等后台服务，具体实现资料未提及 [推测]
  - AI 模型或 API：调用某家 LLM 接口来生成和检查回复，具体厂商资料未提及 [推测]
  - 数据来源：Reddit 的帖子和各版块规则，通过 Reddit 官方接口获取 [推测]

### ⑥ 基于这个灵感的个人项目（STAR 法则）
**项目名 + 一句话描述**：App 发布视频需求分析——用公开 App 评论数据，看用户最在意哪些功能点，帮开发者决定宣传视频里该突出什么。

**S (Situation)**：独立开发者做发布视频时，往往凭感觉决定“视频里先展示哪个功能”，缺少数据依据 [推测]。

**T (Task)**：从公开 App 评论中，量化“功能提及”与“评分”的关系，目标是在测试集上把“差评”识别准确率从 baseline（用来对比的基准成绩） 的 0.60 提升到 0.70 以上，并输出一份“最该在宣传里强调的功能”排序。

**A (Action)**：数据来自 Hugging Face 上的 App 评论数据集 https://huggingface.co/datasets/sealuzh/app_reviews ，含评论文本和星级等字段 （需按数据集卡片确认字段）[推测]。清洗：去重、去空评论、按星级构造“差评/好评”标签。方法：先用 TF-IDF（衡量一个词在文章里有多重要的算法，像给关键词打分）加逻辑回归（估计某件事发生概率的方法，常用来分类）做 baseline，再换一个文本分类模型对比；用 F1（兼顾查得准和查得全的综合分）评估。展示：一张 Dashboard（集中展示关键数字的看板）加一份功能词频与评分关系的分析报告。

**R (Result)**：预期目标：差评识别 F1 从 baseline 0.60 提升到 0.70 以上，并在报告中给出前 10 个高关联功能词及其与评分的相关系数（衡量两个数值同涨同跌程度的指标，取值 -1 到 1，越接近 1 说明功能词出现越多评分越高，越接近 -1 说明反过来，接近 0 说明基本没关系；这里用皮尔逊相关系数），用测试集测量。

**可行性打分**：数据可得性 4/5，公开数据集可直接下载；技术难度 3/5，文本分类是成熟任务；时间成本 4/5，两周可完成；简历加分程度 3/5，题目常见但结论可讲。项目可行性：4/5

**两周执行计划**：第 1–2 天，下载数据、确认字段、做探索分析；第 3–4 天，清洗并构造标签；第 5–6 天，跑 TF-IDF 加逻辑回归 baseline；第 7–9 天，换模型并调参；第 10 天，人工抽查不超过 60 条验证标签质量；第 11–12 天，做误差分析（把模型判错的评论一条条翻出来看，统计错在哪些词、哪些星级上，比如是否总把带讽刺语气的评论判反）；第 13–14 天，写报告、做看板、准备讲稿。

**面试可能被追问的 2 个问题**：
1. 为什么用 F1 而不是准确率？回答方向：差评和好评比例可能不均衡，准确率会被多数类带偏，F1 兼顾查准和查全。
2. 评论里的功能词和评分相关，能说明因果吗？回答方向：不能，只能说明关联，可能存在混淆因素（同时影响两边的第三方原因，比如 App 版本、设备型号、用户群体不同，既改变评论用词也改变打分），需要说明局限。
